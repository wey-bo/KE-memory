**一句话结论**：我们的 **NL2KE 服务**把自然语言问题转成一种结构化、可确定性下游编译的中间语言 **KE**；它既能独立作为「NL→KE」组件供您调用，也自带一套**记忆设施雏形**（业务口径 / 用户偏好 / 本体升格），正好能对接您 Agent 的记忆模块。您问的**「KE 缓存」= 把算过的 NL→KE / KE→SQL 结果按键复用**；**「Memory2KE」= 把 Agent 积累的记忆喂回 NL→KE，让它越用越准**——后者我们已有雏形、但最重的转换环需与您共创。

| 维度 | 内容 |
|---|---|

**数据支撑（为什么这套东西对「记忆/缓存」有价值）**：

## 0. NL2KE 服务是什么（一分钟速览）

我们把「自然语言查数据库」拆成三层，**我们提供的是中间那段 NL→KE**：

```
自然语言(NL) ──①生成──▶ KE（知识表达式，中间语言） ──②编译──▶ SQL ──③执行──▶ 结果
             【NL2KE=我们提供】              KE2SQL(确定性,我们自研)
```

- **KE（Knowledge Equation）**：介于自然语言和 SQL 之间的、结构化、可被确定性编译的中间语言。它比 SQL 更贴近语义、比自然语言更精确，**适合作为「记忆」的存储与复用单元**——比一句自然语言更稳定可比对，比一条 SQL 更能跨库/跨方言迁移。
- **为什么给您 KE 而不是直接给 SQL**：KE 是「意图的结构化沉淀」。您 Agent 记忆里如果存的是 KE，就能被确定性地重编译成 SQL（换库/换方言也行），且能被相似度召回、被校验器验有效性——这是 SQL 文本做不到的。

## 1. NL2KE 服务能产出什么、需要什么（核心契约）

核心是一个**无状态**端点 `POST /v1/ke`（自带 schema 模式，BYOS：调用方自带库结构与本体，问完即清、不连业务库、不持久化）。

**您要给的输入：**

| 字段 | 必填 | 说明 |
|---|---|---|
| `nl_query` | 是 | 自然语言问题 |
| `db_id` | 是 | 本次库结构/本体的标识 |
| `tables_json` | 是 | 库结构（BIRD/Spider 格式：表名/列名/列类型/主外键） |
| `ontology` | 是 | 领域本体 `{concepts, operators}`（决定 KE 用什么概念/算子表达） |
| `evidence` | 否 | **业务口径/外部知识提示**——这里正是「记忆」的注入点之一 |
| `verify` | 否 | 是否走完整校验流程（本体校验+语义校验+失败重生）；关掉更快但不校验 |
| `max_retries` / `use_fc` | 否 | 校验重生轮数 / 是否用 Function-Calling 稳定结构化输出 |

**服务会产出：**

| 字段 | 说明 |
|---|---|
| `ke` | 生成的 KE（核心产物） |
| `verify_passed` | 语义+本体校验是否通过（可作为「是否值得存进记忆」的信号） |
| `attempts` | 生成尝试次数 |
| `reconstructed_nl` | 校验器从 KE 反构出的自然语言（可用于人审/相似度） |
| `reason` | 未通过原因（通过则空） |
| `latency_ms` | 本次耗时 |

> 除 BYOS 外，我们另有一套**有状态服务**（连库、构本体、多轮会话），若您希望我们端到端托管库与本体也可走这条；但对「集成进您的 Agent」，**BYOS 无状态 `/v1/ke` 通常最省事**。

## 2. KE 缓存（您问的第一件事：KE 缓存是什么）

**一句话**：把「算过的结果」按键存下来，命中即毫秒返回、省掉昂贵的大模型/编译。分两层，可分别启用：

- **编译缓存（KE→SQL）**：给定 KE 取回曾编译的 SQL。因 KE2SQL 确定性，`(KE, 方言, 库结构版本)` 相同则 SQL 必然相同——**缓存 100% 正确、无一致性风险**，最安全、最先值得上。
- **生成缓存（NL→KE）**：给定问题取回曾生成的 KE，跳过大模型。含「完全命中直接复用」与「高相似度作参考」两种模式（见 §3）。

**缓存键与失效**：键 = 归一化后的 `KE`（或 `question`）+ `dialect` + `schema/ontology 版本`；**库结构或本体一变，对应缓存即失效**。

**加在哪（两种，供您选）**：
- **加在您侧**：我们给出缓存键归一化规范 + 失效规则 + 参考实现，缓存存储与命中逻辑跑在您的 Agent 里，未命中才回调我们的服务。好处：数据/容量/隔离您掌控。
- **加在我们侧**：您照常调用，我们服务端透明缓存，响应带 `cache_hit` 标记。好处：零集成成本。

## 3. Memory2KE（您问的第二件事：把记忆喂回生成）

**一句话**：把您 Agent 积累的「记忆」转化为能提升 NL→KE 质量的输入，让生成**越用越准、越省**。我们已有三条现成通道，对应记忆的不同形态：

| 记忆形态 | 喂回通道（已有代码） | 效果 |
|---|---|---|
| **历史问答对（NL↔KE）** | 相似历史召回作 few-shot / 高相似直接复用 | 覆盖率 98%、省 token ~89% |
| **业务口径 / 领域知识** | `evidence` 字段注入 + evidence 端点沉淀 | 让生成贴合您的口径 |
| **用户偏好 / 反复纠正** | preferences 端点（用户级 & 会话级）→ ontology-evolution 提炼成本体升格建议 | 纠错沉淀为长期本体资产 |

**最重、需共创的一环**：把您 Agent 里**任意形态的记忆**（可能是对话、文档、行为日志）转成**合法 KE 或有效本体片段**——这一步的难度完全取决于您的记忆长什么样，是本方案唯一需要与您共创、我们不夸大即用程度的部分。**建议：先拿您 2–3 个真实记忆样例，我们做一次转换 PoC，用真实数字判定可行度**，再决定投入。

## 4. 有效性校验（复用记忆不出错的保险）

复用旧 KE 有个风险：库结构演进后，旧 KE 可能失效。我们用**编译器当闸门**：
- 旧 KE 复用前先过 KE2SQL 编译，**编不过就拦下**，并返回**结构化报错**（区分「输入非法 / 本体缺算子 / 语言不支持」）；
- 配合定向修复：报错能定位到该修哪、甚至提示补哪个算子。

对您的价值：记忆越攒越多也不会「越攒越脏」——失效的会被自动挡在门外或定向修好。

## 5. 集成形态（供挑选）

| 形态 | 说明 | 适合 |
|---|---|---|
| **只要 NL→KE 组件** | 调 `POST /v1/ke`，缓存/记忆逻辑在您的 Agent 里 | 您已有记忆体系，只缺「NL→KE」这段能力 ← 按您描述最可能是这个 |
| **NL→KE + 记忆设施** | 连 evidence/preferences/evolution 一起用 | 您想直接复用我们的记忆沉淀端点 |
| **端到端托管** | 我们连库、构本体、多轮会话全包 | 您想一站式、少自建 |

接入方式：HTTP 服务（同现有风格，最省事）/ Python SDK / 批量离线。

## 6. 需要确认的点

1. **您要哪种集成形态**（§5 三选一）？按您「在做 Agent 记忆模块」的描述，我们**推测是「只要 NL→KE 组件」**——请确认。
2. **您的「记忆」具体是什么**：历史问答对 / 对话上下文 / 领域文档 / 用户行为日志？（决定 Memory2KE 转换难度）
3. **KE 缓存加在您侧还是我们侧**？
4. **库结构与本体谁提供**：您自带（BYOS）还是我们构建？
5. **复用信任度**：高相似历史 KE 是「直接复用免大模型」还是「仅作参考」？（省钱幅度 vs 正确率权衡）
6. **数据与隔离**：多租户/多库隔离？记忆是否含敏感数据（影响能否缓存原文）？
7. **时效**：旧口径如何过期/遗忘？库结构演进时缓存/记忆的失效策略？
