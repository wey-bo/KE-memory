# Authoritative Memory Contract v3 Design

Status: frozen for implementation after the raw-source/revision, closure-freshness, and structured-L2 audits.

## Goal

Add an authoritative, representation-independent memory bundle beside the existing v2 conformance bundle. The new bundle must make raw-source binding, immutable unit revision history, structured L2 semantics, and closure-evaluation freshness executable. Existing v2 and v4 artifacts remain immutable audit evidence.

This wave does not select a production database, run model extraction, rerun external memory systems, or claim benchmark/product superiority.

## Alternatives

### Mutate the v2 bundle in place

Rejected. Adding mandatory revision and closure fields to v2 would change the bytes generated by the frozen v4 run and make its audit trail non-reproducible.

### Keep v2 and put authority fields in free-form metadata

Rejected. Metadata that is copied but not validated, queried, and freshness-checked does not satisfy the memory contract.

### Add a parallel v3 authoritative bundle and explicit migration

Selected. V2 remains readable. A deterministic migration builds v3 from a v2 bundle, the frozen source manifest, the frozen evidence corpus, a fixed transaction time, explicit producer identity, and explicit L2 claim mappings.

## Layers

```text
frozen raw artifact
  -> immutable source-record revision
  -> exact EvidenceSpanV2
  -> immutable L1/L2 unit revision
  -> materialized current view
  -> ClosureSpec
  -> ClosureEvaluation
  -> representation-independent query executor
  -> Extended-AMR v2 physical graph
```

The raw artifact is the recovery anchor. A source-record revision is a deterministic normalized view produced by a versioned resolver. Evidence offsets are Unicode code-point offsets into that normalized record; they are not claimed to be raw-file byte offsets.

## Raw-source and revision ledger

`RawArtifactRevision` records the frozen identity, official URL, workspace-relative path, reader, size, and SHA-256 of one raw artifact.

`SourceRecordRevision` records a stable logical source-record ID, immutable revision ID, sequential revision number, parent revision, raw artifact revision, source reference, normalized text and hash, resolver identity/version, transaction time, and source metadata.

`EvidenceSpanV2` adds three mandatory fields to the v1 evidence coordinates:

- `source_revision_id`;
- `quote_sha256`;
- `offset_unit = unicode_codepoint`.

Validation reopens the artifact inside the configured workspace root, verifies file size/hash, reruns the declared resolver, compares the reconstructed normalized source record, and verifies the exact quote slice and quote hash.

`MemoryUnitRevision` records stable logical unit identity separately from immutable revision identity. Revision 1 has no parent; later revisions are sequential and form one linear chain. Its payload is a typed L1 or L2 unit, with a canonical payload hash, source revision IDs, derived-from unit revision IDs, transaction time, revision kind, and producer identity.

The v3 bundle retains `l1_units` and `l2_units` only as current materialized views. `canonical_json_bytes(view)` must equal `canonical_json_bytes(selected_revision.payload)` for every entry selected by `current_revision_ids`. Current pointers must target leaf revisions. Semantic `supersedes` links never substitute for storage revision parents.

## Structured L2 semantics

L2 display strings are not authoritative claims. `L2MemoryUnitV2` therefore separates:

- `summary` and `display_assertions`, for human display and audit;
- `structured_claims`, for query execution.

Each `L2StructuredClaim` has a stable claim ID, typed predicate, role bindings, modality, polarity, exact event/valid/transaction time fields, and a non-empty list of supporting L1 units. Optional aggregate semantics are a separate typed object; a count query cannot be satisfied by a non-aggregate claim. A semantic L2 query matches only if at least one structured claim satisfies every supplied constraint and answer shape. Evidence is returned only from the matched claim's pinned supporting L1 revisions.

The current LongMemEval fixture contains the display assertion `count(led_projects_by_user)=2`, while its four L1 events currently use four distinct provisional project IDs. V3 must not promote that count to a structured claim until project identity/deduplication is explicitly represented. The safe structured claim in this wave is only the supported `lead/manage` abstraction with `user` as leader and all four L1 events as support. Its count query must return the evidence candidates but abstain with `structured_l2_identity_unresolved`.

## Authoritative query plan

`AuthoritativeQueryPlan` is separate from the v1 query model so frozen v2 serialization does not change. It supports:

- target level, entity IDs, predicate sense, canonical operator, and exact role constraints;
- modality and polarity;
- typed exact event/valid/transaction time constraint;
- source-status and lifecycle constraints;
- answer shape (`fact`, `evidence_set`, or `count`), closure spec ID, and guarded-fallback policy.

L1 and L2 claims use one semantic matcher. A constrained query cannot match a display-only L2. An unconstrained migration-only query may inspect such a record, but it cannot treat display strings as facts.

## Closure specification and evaluation

`ClosureSpec` contains stable closure identity, monotonic spec revision, one explicit target ID, closure pattern, explicit slots, and a canonical spec hash. Every slot has stable identity, role, required flag, optional bound logical unit ID, and fallback classification (`blocked` or `candidate_only`). Missing causal-link structure is a real unbound slot, not a fabricated memory-unit ID. Any change to slot identity, role, required flag, binding, or fallback class requires a new spec revision; an old revision is immutable.

Claim admission and query answerability use separate discriminated contexts:

- `ClaimClosureContext`: L2 unit ID, claim ID/hash, pinned support unit revisions, and support scope;
- `QueryClosureContext`: query plan ID/hash, query scope, and available unit IDs.

An active L2 can reference only a fresh claim-context evaluation. A query can use only a fresh query-context evaluation. For the one real-slice L2, migration derives a claim-targeted spec for admission and a separate query-targeted spec for retrieval/answerability; it does not make a claim depend on an arbitrary query.

`ClosureEvaluation` is an immutable calculation record containing:

- deterministic evaluation ID;
- closure/spec revision and hash;
- evaluator and policy versions;
- evaluated bundle ID;
- a typed claim or query context;
- dependency revision/content hashes;
- per-slot results;
- an `input_fingerprint` over spec, evaluator/policy, target context, scope, availability, and dependency revisions/hashes;
- derived completeness, fallback decision, reason code, and a separate `result_hash`.

`evaluation_id` is the SHA-256 identity of the canonical input fingerprint. Freshness compares the current input fingerprint to the persisted one. Recalculation parity separately compares `result_hash`; matching input identity does not excuse a changed derived result. An evaluation becomes stale when the spec, policy/evaluator, target claim/query, scoped plan, scoped available units, bound unit revision/content, referenced source revision/content, or slot binding changes. Changes outside the context scope do not make it stale.

A stale evaluation cannot support active L2, cannot authorize an answer, and cannot trigger embedding fallback. It must be recomputed first.

## Integrity gates

The v3 structural validator rejects:

- duplicate/conflicting artifact, source, unit revision, claim, spec, evaluation, or query IDs;
- non-linear, cyclic, branched, or gapped unit/source revision chains;
- incorrect canonical hashes or current pointers;
- current views that differ from selected revision payloads;
- evidence spans that do not match source revision text/hash;
- L2 claim support outside `source_l1_units`, outside the L2 pinned source revisions, or outside the fresh evaluation's resolved slot revisions;
- L2 derivation revisions that fail to pin its source L1 revisions;
- active L2 whose `closure_id`, `closure_spec_revision`, or `closure_evaluation_id` does not resolve to the same fresh claim-context evaluation;
- constrained queries that could only match display text.

Authoritative source validation additionally verifies file containment, size/hash, and resolver replay.

## Extended-AMR v2

`extended-amr-memory-graph-v2` is a new physical profile; v1 stays read-only.

The payload carries typed top-level raw artifact revisions, source record revisions, closure specs, closure evaluations, authoritative queries, scopes, explicit `current_revision_ids`, and unit-revision headers. It does not embed opaque L1/L2 payload copies.

Each unit revision is represented as a graph:

- L1: predicate node, entity nodes, typed role edges, and typed memory/source/evidence annotations;
- L2: abstraction node, explicit claim-predicate nodes, claim entity nodes, typed role edges, support-reference edges, source-reference edges, and display-only annotations;
- L2 abstraction edges explicitly reference both closure spec and closure evaluation.

Historical unit revisions receive their own graphs. Decoding reconstructs every revision payload from its graph, rebuilds current views from current pointers, and then runs v3 integrity/freshness checks.

## V5 conformance decision

V5 compares the native v3 carrier and Extended-AMR v2 using:

- exact logical round-trip;
- five scoped query-result parity probes;
- five frozen correctness expectations covering matched units/claims, evidence set, abstention, closure result, fallback authorization, and reason code;
- source/revision integrity;
- closure evaluation freshness and recomputation parity;
- stale/incomplete active-L2 rejection;
- `fallback_allowed=false` and zero fallback triggers for structural gaps.

Capability declarations are not self-certifying. The report promotes a capability only when its corresponding gates pass.

The expected result is evidence-driven, not preselected. The unresolved count probe is frozen to abstain with `structured_l2_identity_unresolved`; adapter parity without this correctness result fails. The report must retain `authoritative_ready=false` and identify that reason rather than weakening the gate.

Legacy v2 `ClosureRecord.complete`, `missing_slots`, and `reason` are audit inputs only. Migration constructs immutable v3 specs and recomputes every v3 evaluation with the fixed v3 evaluator/policy and current pinned dependencies. Changing a legacy materialized result must not change the v3 recomputation.
